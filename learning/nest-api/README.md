# Streamroom — NestJS API, етап 1

Окремий навчальний Node.js проєкт, не частина серверного середовища Lovable.
AI-assisted код: перед використанням у портфоліо прочитай, зміни й поясни рішення сама.

## Межі цього етапу

Працюють GET /rooms, GET /rooms/:id/messages і POST /rooms/:id/messages.
Дві кімнати — навчальні дані; створення кімнат і вступ не реалізовано.
Дані лише в пам’яті: перезапуск стирає повідомлення. PostgreSQL, логін,
redux-saga та LiveKit ще НЕ підключені. Браузерний чат не звертається до цього API.

Сервер слухає тільки 127.0.0.1:3001. Не публікуй його в інтернеті й не змінюй
адресу на 0.0.0.0: справжньої автентифікації немає. demo-host — фіксований
навчальний користувач. Перевірка членства — авторизація щодо цієї фікстури,
а не доказ особи. Навіть заголовок Authorization тут не перевіряється.

## Запуск на твоєму комп’ютері

Потрібен Node.js 22 або новіший. Розпакуй архів, відкрий термінал у nest-api:

```sh
node --version
npm ci
npm test
npm start
```

`npm test` компілює окремий API та запускає 18 тестів. `npm start` запускає
скомпільовані файли. Після змін знову виконай npm test, тоді npm start.
Зупинка — Ctrl+C. Другий термінал — для запитів.

```sh
curl -i http://127.0.0.1:3001/rooms
curl -i -X POST http://127.0.0.1:3001/rooms/room-001/messages \
  -H 'Content-Type: application/json' -d '{"text":"  Привіт API  "}'
curl -i http://127.0.0.1:3001/rooms/room-001/messages
curl -i -X POST http://127.0.0.1:3001/rooms/room-002/messages \
  -H 'Content-Type: application/json' -d '{"text":"Привіт"}'
```

Очікування: 200 (кімнати), 201 (створення, text без пробілів по краях),
200 (читання з тим самим id), 403 (інша кімната). У Windows PowerShell
використай curl.exe замість curl; JSON також можна надсилати через Postman.

## Чому так

Запит → Controller → DTO/ValidationPipe → Service → пам’ять → відповідь.

- **AppModule** реєструє controller і service. Nest сам передає service через
  конструктор: dependency injection дозволяє замінювати залежність у тестах.
- **Controller** описує HTTP маршрути й передає вхід у service. Логіка доступу
  не дублюється в кожному маршруті.
- **DTO** перевіряє форму зовнішнього JSON під час виконання. TypeScript сам
  цього не робить: типи зникають після компіляції.
- **ValidationPipe** увімкнено і в main, і в HTTP тестах через configureApp.
  trim виконується до перевірки. Ліміт 1–500 — вибір для цього навчального етапу;
  Length використовує семантику validator.js, не кількість видимих emoji.
  Невідомі поля (зокрема authorId) дають 400, а не мовчки приймаються.
- **Service** перевіряє існування кімнати і членство до читання/запису.
  Це демонструє авторизацію. В production userId має надходити з перевіреної
  сесії, а не з JSON, довільного заголовка чи цієї фіксованої константи.
- **Map** тимчасово замінює сховище, щоб спочатку зрозуміти HTTP і тести.
  Видаємо копії повідомлень, щоб виклик не змінював внутрішні об’єкти напряму.
- **Unit тести** перевіряють service без HTTP. **HTTP тести** піднімають справжній
  Nest застосунок через testing module, проходять через маршрути й валідацію.
  Це не перевірка браузера, БД, справжнього логіну чи навантаження.

## Твоя практика — зупинись тут перед наступним етапом

1. Запусти npm test. Збережи підсумок; якщо помилка — надішли її без секретів.
2. Надішли повідомлення через curl або Postman й прочитай його другим запитом.
   Перевір порожній текст (400), room-002 (403) і missing (404).
3. Відкрий test/rooms.http.test.ts. Додай окремий HTTP тест для
   `{ "text": true }`: очікується 400. Спочатку запусти тест з очікуванням 201
   і переконайся, що він падає; поверни 400 — він має пройти.
4. Поясни своїми словами: чому `text: string` не захищає від JSON з числом?
   Чому authorId не приймаємо від клієнта? Що зникне після перезапуску?
   Чим відрізняються 400, 403 та 404 у цих запитах?
5. Надішли результат тестів, свій новий тест і відповіді. Наступний крок — лише
   після розбору твоєї практики: сховище PostgreSQL і справжня ідентифікація.

Не записуй цей етап у CV як production або досвід потокового відео.
